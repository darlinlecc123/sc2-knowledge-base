# 公众号文章草稿：让大模型真正读懂 STORM 中的 StarCraft II 变量

> 状态：大纲与初稿，尚未发布。正式发布前需确认许可证、作者署名、GitHub 地址和可公开的评测材料。

## 备选标题

1. 我们给 StarCraft II 智能体做了一本“变量字典”
2. 从自然语言到源码证据：面向 LLM Agent 的 STORM Raw API 知识库
3. 大模型能否准确找到 StarCraft II 环境变量？我们做了一个可检索知识库

## 一、为什么需要这个知识库

在强化学习和大模型智能体项目中，一个常见问题不是“模型会不会写答案”，而是它能不能准确回答：某个自然语言概念对应哪个接口字段、字段在代码哪里被读取、经历了什么转换、最后又影响了哪个动作或实验指标。

以 STORM 为例，“单位血量”“动作延迟”“位置误差”看似简单，但可能分别处于 PySC2 Raw API、ABox、动作协议和 SWM 指标等不同层级。如果只把长文档一次性塞给模型，模型可能混淆层级、漏掉变量，或者给出没有依据的解释。

## 二、我们整理了什么

第一版只覆盖当前 STORM 主路径实际使用的 Raw API 变量及直接衍生量，不追求完整 PySC2 百科。候选版包含：

- 135 个正式变量；
- 1430 条来源、映射、派生、校验和执行关系；
- 11 个已知问题；
- 中文、英文、代码字段和口语别名；
- 本地检索器、LLM 上下文、QA Agent 和自动评测工具。

每条记录不仅回答“它是什么”，还尽量回答“从哪里来、代码在哪里、如何转换、用于什么、有什么限制”。

## 三、一个查询示例

用户问：

> 单位当前血量对应哪个字段？

知识库可以检索到 `raw_unit.health`，解释它来自 RawUnit 的当前生命值字段，并返回 STORM 中的读取和映射证据。对于代码现实与设计意图不一致的地方，回答会明确区分，而不是自动把异常实现解释成标准语义。

## 四、为什么采用 RAG

RAG 是 Retrieval-Augmented Generation，即“检索增强生成”。系统先从知识库中挑出与问题相关的变量、关系和证据，再让模型基于这些材料回答。

与 no-KB 和 full-context 相比：

- no-KB 用来检验模型只靠预训练记忆是否认识项目专用变量；
- full-context 把完整知识上下文一次性交给模型，用来观察知识上界、长上下文稳定性和成本；
- RAG 只提供相关证据，目标是在较低 Token 成本下保持准确性与可追溯性。

## 五、测试结果

在优化后的 DeepSeek v4 Flash challenge v0.6 回归对照中：

| 条件 | 行为准确率 | 变量召回率 | 变量精确率 | 证据命中率 | Token |
|---|---:|---:|---:|---:|---:|
| no-KB | 25.00% | 10.00% | 10.00% | 0.00% | 29,271 |
| full-context | 56.67% | 70.00% | 70.00% | 58.33% | 1,779,558 |
| RAG | 90.00% | 84.03% | 94.67% | 96.06% | 178,867 |

RAG 比 full-context 节省 89.95% Token，并取得更高行为准确率。不过，这一结果是调参后的回归对照，不等于无偏泛化结论。

在 challenge v0.6 唯一一次首次盲测中，六项冻结指标有四项通过，变量召回率 84.03% 略低于 85% 门槛，原生 JSON 合规率 98.00% 略低于 99% 门槛。因此我们的正式结论是：**知识库和 RAG 已显示明显价值，但尚未达到全部预声明的“有效 RAG”门槛。**

## 六、我们如何防止“为了测试题调答案”

挑战集在测试前冻结，并保存哈希和收据。首次盲测后不再把同一题集的结果冒充新的泛化证据；若依据该题集修复系统，它只能作为回归集。下一次泛化判断需要冻结全新题集，并只进行一次首次盲测。

## 七、当前局限

- 正式许可证、作者和版权主体尚待负责人确认；
- full 包在干净目录运行部分测试时仍有导入路径问题；
- Windows 默认 GBK 下，含数学字符的完整 JSON 输出可能报编码错误；
- 多变量问题仍有少量漏召回；
- 某些 PySC2 Function ID 和 ontology cache 一致性需要固定版本和真实 SC2 环境验证；
- 本项目不是 Blizzard、DeepMind 或 PySC2 的官方知识库。

## 八、如何参与

公开后，研究者可以通过 Issue 提交：

- 自然语言漏召回或误召回；
- 新变量及其源码证据；
- 接口版本差异；
- 数据流和公式关系修正；
- Windows/Linux 可移植性问题。

所有变量变更都必须附当前源码路径、稳定符号、接口形式、事实状态和离线验证结果。

## 九、结尾

这个项目的目标不是让大模型“看起来懂 StarCraft II”，而是让它在回答项目变量问题时能够找到正确物理量、指出接口、定位实现，并给出可以被人复核的依据。

GitHub 地址、许可证和维护者名单将在负责人确认后补充。
