# 贡献指南

感谢你帮助维护 STORM PySC2 Raw API 变量知识库。贡献的首要目标不是扩大条目数量，而是让每条记录都能被源码、配置、测试或运行证据核查。

## 1. 范围边界

V0.1 只接收当前 STORM 主路径实际读取、转换、生成、校验或使用的 Raw API 变量及直接衍生量。以下内容默认不进入正式变量集：

- 仅由 PySC2 提供、但当前 STORM 未使用的字段；
- Feature Layer 像素变量；
- StarCraft II 百科内容；
- 无源码位置、无版本依据的记忆性描述；
- 只存在于任务说明或设计文档、但未在代码实现的字段。

如需扩展范围，请先提交范围变更 Issue，不要在单个变量 PR 中静默扩展。

## 2. 贡献流程

1. 先搜索现有变量 ID、别名和已知问题，避免重复。
2. 创建变量请求或缺陷 Issue，说明动机和证据。
3. 修改机器可读记录，再同步别名、关系、文档与测试。
4. 运行离线检查，并在 PR 中粘贴命令和真实结果。
5. 由维护者执行证据审查、范围审查和兼容性审查。
6. 合并后更新 CHANGELOG；涉及破坏性 Schema 变化时按版本策略升级。

## 3. 变量新增或修改的证据要求

每个变量至少应包含：

| 项目 | 要求 |
|---|---|
| 稳定 ID | 遵守 taxonomy 和 naming rules，不因措辞变化重命名 |
| 定义 | 区分物理含义、接口编码和 STORM 内部语义 |
| 接口 | 类型、形状、单位、范围或枚举；未知时明确标记 |
| 实现位置 | 相对 STORM 根目录的源码路径与稳定 symbol |
| 证据 | 当前源码优先；其次为本地依赖/API 定义、运行结果和项目文档 |
| 生命周期 | 来源、归一化、映射、派生、校验或动作执行路径 |
| 事实状态 | `design_intent`、`code_reality`、`runtime_observation` 或 `needs_verification` |
| 检索入口 | 中文、英文、代码名、口语别名和必要的反例 |
| 关系 | 至少检查 `source_of`、`normalized_to`、`mapped_to`、`derived_into`、`validated_by`、`executed_as` |
| 测试 | Schema、关系端点、检索与证据绑定测试 |

不要伪造精确行号。若行号易漂移，记录文件、类、函数或符号即可。

## 4. 证据优先级

1. 当前 STORM 源码和配置；
2. 当前安装或锁定版本的 PySC2/SC2 API 定义；
3. 实际测试和运行产物；
4. 当前项目文档；
5. 旧说明文档或外部常识，仅作补充并标注。

PR 不得把 README 或任务提示词中的设计描述直接提升为运行时事实。

## 5. 必须同步检查的文件

变量发生变化时，按影响检查：

- `variables/*.yaml`
- `lineage/variable_lineage.yaml`
- `retrieval/aliases.yaml` 与查询模式
- `relations/variable_relations.jsonl`
- `known_issues.yaml`
- `docs/variable_catalog.md`、`docs/glossary.md`、`docs/dataflow.md`
- 上下文包和离线测试

派生文档应由现有生成脚本更新，不要手工制造与机器记录不一致的副本。

## 6. 本地验证

从知识库根目录运行，命令的目的是检查 Python 语法、Schema、检索、关系和发布边界：

```powershell
python -m py_compile scripts/validate_github_release.py
python scripts/validate_github_release.py
```

如果修改了发布包，还应运行步骤 18 的构建与验证脚本。不要声称未实际运行的命令已经通过。

## 7. PR 审查门禁

维护者至少检查：

- 是否仍在 V0.1 范围；
- 是否有当前源码证据；
- 是否区分设计、实现、运行与待验证事实；
- 变量 ID、别名和关系端点是否一致；
- 是否包含不必要的绝对路径、密钥、日志、缓存或模型原始回答；
- 是否降低冻结测试门槛或根据盲测题进行过拟合；
- 是否清楚说明兼容性和已知问题。

## 8. 版本策略

采用语义化版本思想：

- PATCH：定义澄清、别名补充、证据路径修正、非破坏性检索修复；
- MINOR：向既定范围增加变量族、关系类型或向后兼容能力；
- MAJOR：Schema、稳定 ID、接口契约或知识范围发生破坏性变化。

冻结 challenge 的答案或评分协议发生变化时，不得只做静默 PATCH；必须保留旧版本收据并说明原因。

## 9. 行为规范

使用专业、可复核和尊重性的语言。争议应回到证据与复现实验，不以模型猜测或个人权威替代证据。
